# Project Registry implementation plan

## Goal

Replace both the current in-memory `project-registry` package and the separate `caddy-projects` application with one machine-wide Project Registry.

Project Registry will provide:

- One authoritative Git-backed project catalog.
- All current `caddy-projects` behavior, including project CRUD, Caddy configuration generation, validation, reload, documentation routes, OIDC routes, config inspection, port allocation, and history.
- All current `software` behavior, including project grouping, ordering, links, UI preferences, service status, and user-level systemd actions.
- One CLI and one web UI.
- Multi-user access based on Linux users and current Zitadel roles.
- A one-time migration that preserves the existing Caddy data repository and imports legacy Software YAML.

The source stays modular. Top-level source folders represent bounded contexts, not broad technical layers.

## Decisions

### Product boundary

- `project-registry` replaces `caddy-projects`; it does not depend on or call a running `caddy-projects` daemon.
- Caddy project schema, generation, validation, reload, docs, OIDC, CLI, daemon, and API behavior move into this repository.
- After cutover there is one daemon, one set of per-user sockets, one CLI, one UI, and one project-data Git repository.
- Project Registry calls the Caddy admin API directly after generating and validating the complete desired configuration.
- Direct changes to Caddy's live configuration are temporary. Startup, project mutations, and periodic regeneration restore the registry's authoritative configuration.
- The old `caddy-projects` daemon and sockets are removed after migration. Its source repository and pre-migration data backup remain read-only during the rollback period.
- The old `software` local-password login is removed. Zitadel is the only browser identity provider.
- The current `@adaptive-ds/project-registry` singleton `Map` API may be removed. Version `0.1` does not constrain the replacement architecture.

### Source organization

- Use bounded-context folders directly under `src/`: `project`, `project-store`, `access`, `identity`, `zitadel`, `session`, `caddy`, `service`, `user-systemd`, `history`, `api`, `socket`, `web-server`, `runtime`, `cli`, and `legacy-migration`.
- Do not create global `domain`, `application`, `infrastructure`, `utils`, `helpers`, or `shared` dumping grounds.
- Each context owns its model, validation, use cases, and interfaces. Runtime adapters implement interfaces without leaking Bun, Git, Zitadel, Caddy, or systemd details into project rules.
- Keep one export per file and subject-first filenames.
- Fallible operations return `Result` or `PromiseResult`; expected failures do not use exceptions.
- Keep `.tsx` files view-only. UI state, requests, transformations, and actions live in `.ts` files beside their views.
- Unit tests stay beside the source they cover. Cross-context, migration, daemon, and browser tests live under `test/`.

### Identity and access

- Zitadel defines three Project Registry roles: `own`, `admin`, and `superadmin`.
- Each Zitadel user maps 1:1 to a Linux user. `preferred_username` must exactly match an existing POSIX username.
- Zitadel `sub` is the stable browser identity. Linux username is the project owner, CLI identity, socket owner, and systemd target.
- Project files do not store user roles. Authorization resolves the owner's and actor's current Zitadel roles.
- If Zitadel returns multiple roles, precedence is `superadmin`, then `admin`, then `own`.
- An invalid mapping, missing role, removed user, or unavailable role lookup fails closed. Projects with an unresolved owner are accessible only to a superadmin.
- An `own` user can manage only their projects and services.
- An `admin` can manage projects and services owned by current `own` and `admin` users. An admin cannot see or operate projects owned by a current `superadmin`.
- A `superadmin` can manage every project and service and run machine-wide administrative operations.
- Access follows the owner's current Zitadel role. Changing that role changes protection without rewriting projects.
- Projects are private to their owner. There is no shared-project or template visibility model.
- An `own` user sees only their projects and no user tabs.
- An `admin` sees one tab for every visible non-superadmin user.
- A `superadmin` sees one tab for every mapped user.

### Project model

- A project key is `(owner, name)`.
- The owner and name are immutable. Rename or ownership transfer is an explicit create-and-delete workflow.
- Names use `^[a-z0-9][a-z0-9-]*$` so every project can participate in Caddy configuration without a second identity.
- Each project document has `schemaVersion`, `owner`, `name`, optional `description`, registry metadata, service declarations, links, and optional Caddy settings.
- Registry metadata contains:
  - `type`: `own`, `internal`, or `customer`; default `customer`
  - numeric `order`
  - deduplicated `services`
  - optional `github`
  - optional `previewUrl`
  - optional `previewPort`
  - optional `productionUrl`
  - optional `productionAssetsUrl`
- A missing `caddy` value means Project Registry catalogs the project but generates no Caddy route.
- Caddy settings contain:
  - `port`
  - non-empty `domains`
  - `path`
  - `access`: `internal` or `external`
  - `kind`: `proxy` or `static`
  - `docs`
  - `browse`
  - `headerUp`
  - `disabled`
  - optional `routed`
  - optional `oidcPaths`
  - optional `docsPath`
  - optional `browseTemplate`
  - optional `staticAllow`
  - optional `denyDotfiles`
  - optional `spa`
  - optional `flushInterval`
- `owner` and `name` replace the old nested Caddy `user` and `name` fields.
- The new schema has no `shared` or `template` fields.
- Active ports and domains are unique across all users. Disabled projects do not reserve them.
- Omitted ports on Caddy-enabled project creation receive the lowest available port in the configured allocation range, initially `3000-3999`.
- Project ordering remains compatible with Software: group order `internal`, `customer`, `own`; then numeric `order`; then name.
- Service unit names must match `^[A-Za-z0-9_.@:-]+(?:\.service)?$`.

### Git-backed project store

- Use the existing Caddy project data repository as the initial Project Registry data repository so its Git history and remote remain intact.
- Current records remain under `projects/<owner>/<name>.json`. Migration transforms their schema in place and adds Software metadata.
- New registry-only projects use the same path convention.
- Store migration metadata under `migrations/legacy-v1.json`.
- One daemon process owns the worktree. A global mutation queue serializes validation, file changes, staging, commits, and pushes because `@adaptive-ds/git-store` has no transaction or process lock.
- Each changed create, edit, or delete produces one commit. Identical writes produce no commit.
- Commit messages include the action, project key, and actor. Git author remains the fixed daemon identity `project-registry <project-registry@localhost>`.
- Auto-push is configurable. A failed push does not erase or misreport a successful local commit.
- Startup checks for a clean worktree. Readiness remains false until a dirty worktree is repaired or explicitly recovered from `HEAD`.
- Project history uses Git path history and applies the same owner visibility policy as project reads.
- Data validation reads all current project files before accepting a mutation so global Caddy collisions cannot enter the authoritative branch.

### Caddy ownership

- The `caddy` bounded context absorbs the pure configuration functions and runtime adapters from `caddy-projects`.
- It generates one complete deterministic Caddy JSON configuration from all active registry projects.
- It preserves the existing proxy, static file, docs, browse, SPA, dotfile denial, static allowlist, upstream-header, flush interval, internal-access, and path-scoped OIDC behavior.
- Active projects sort deterministically by domain before route generation.
- Caddy listens on the configured HTTPS listener, initially `:443`.
- Proxy projects target `localhost:<port>`. Static projects use their configured root path.
- Internal routes use the configured Caddy OIDC handler and environment-provided issuer/client settings.
- Documentation URLs and generated-config inspection are derived from registry visibility. Users cannot inspect routes owned by inaccessible users.
- Every desired-state application runs `caddy validate` before calling the Caddy admin `/load` endpoint.
- The registry commit is authoritative. Validation or reload failure does not roll back it. The daemon keeps the last accepted live Caddy configuration, marks application pending, and retries.
- Regeneration runs at startup, after Caddy-relevant mutations, on an explicit command, and periodically to overwrite direct live Caddy edits.
- Metadata-only changes that cannot affect generated Caddy output do not force a reload.
- One Caddy application queue prevents overlapping validation and reload operations.
- Runtime status records the desired registry revision, applied revision, last attempt, last success, and sanitized error. Runtime status is not committed to Git.

### Service ownership

- The project's `services` array is the complete allowlist for service status and actions.
- The daemon runs `systemctl --user` as the target project owner through `runuser`.
- It sets the target `HOME`, `USER`, `LOGNAME`, `XDG_RUNTIME_DIR=/run/user/<uid>`, and `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/<uid>/bus`.
- Process execution uses argument arrays, fixed commands, explicit timeouts, and no shell interpolation.
- Supported actions remain `start`, `stop`, and `restart`.
- Status distinguishes missing units, enabled state, running state, memory use, and query errors.
- Actions wait for systemctl and then return a new status instead of reporting an optimistic success.
- Admin and superadmin operations always execute as the project owner, not the actor and not root's user manager.

### Daemon and transports

- A root-owned `project-registryd` replaces `caddy-projectsd` and the Software user service.
- It creates `/run/project-registry/<linux-user>.sock` with mode `0600` and ownership assigned to that Linux user.
- CLI identity comes only from the selected socket listener. Request data may select a target owner only after role authorization.
- The CLI resolves sockets in this order: `--socket`, `PROJECT_REGISTRY_SOCKET`, `/run/project-registry/$USER.sock`.
- A loopback HTTP listener serves the browser API, OIDC callbacks, and built UI. Caddy owns public TLS and proxying.
- Bun uses one versioned request handler for HTTP and Unix sockets.
- The daemon configuration covers repository path, users/socket directory, web listener, Caddy binary, admin URL, HTTPS listener, port range, OIDC handler settings, Git push mode, and regeneration interval.
- The daemon handles shutdown by stopping new mutations, completing the active Git operation, ending Caddy application safely, closing listeners, and removing stale sockets.

### API and CLI

- Responses use a stable JSON success/error envelope with machine-readable codes.
- Mutations accept an expected Git revision. A stale edit returns `409` rather than overwriting a newer change.
- Core routes are:
  - `GET /health/live`
  - `GET /health/ready`
  - `GET /api/v1/session`
  - `GET /api/v1/users`
  - `GET /api/v1/users/:owner/projects`
  - `POST /api/v1/users/:owner/projects`
  - `GET /api/v1/users/:owner/projects/:name`
  - `PATCH /api/v1/users/:owner/projects/:name`
  - `DELETE /api/v1/users/:owner/projects/:name`
  - `GET /api/v1/users/:owner/projects/:name/history`
  - `GET /api/v1/users/:owner/projects/:name/docs`
  - `GET /api/v1/users/:owner/services`
  - `POST /api/v1/users/:owner/projects/:name/services/:unit/actions`
  - `GET /api/v1/caddy/config`
  - `GET /api/v1/caddy/status`
  - `POST /api/v1/caddy/regenerate`
  - `GET /login/zitadel`
  - `GET /login/zitadel/callback`
  - `POST /api/v1/logout`
- The CLI combines both prior tools:
  - `project-registry user list`
  - `project-registry project list|get|create|edit|delete`
  - `project-registry project history`
  - `project-registry service list|start|stop|restart`
  - `project-registry docs`
  - `project-registry config`
  - `project-registry regenerate`
  - `project-registry status`
- Reads support stable JSON output for scripts. Human-readable output remains the default.
- Existing `caddy-projects` command behavior maps to the new commands, but the old executable does not remain a second maintained client.

### Web authentication and UI

- Browser authentication uses Zitadel Authorization Code with PKCE, state, nonce, exact issuer/audience checks, and exact callback URIs.
- The server stores opaque sessions. It stores subject and token references, not an authoritative role snapshot.
- Cookies are `HttpOnly`, `Secure`, `SameSite=Lax`, and host-scoped.
- Mutations require exact-origin checks and CSRF tokens.
- The UI remains Solid with Vite and preserves Software behavior:
  - cards and table views
  - German labels
  - internal, customer, and own groups
  - stable ordering
  - preview, production, production-assets, and GitHub links
  - optional GitHub and service sections
  - light and dark themes
  - immediate service loading and 15-second polling
  - installed, enabled, running, stopped, memory, pending, and error states
  - start, stop, and restart controls
- Existing localStorage preference keys remain supported.
- The UI adds role-filtered user tabs, project CRUD, all Caddy settings, history, generated-config inspection, Caddy application status, and manual regeneration for superadmins.
- Hidden users and projects are filtered by the API rather than hidden only in the browser.

### Migration and cutover

- Migration code lives under `src/legacy-migration` and is removed from normal daemon startup paths.
- The migration accepts the existing Caddy data repository and `/home/david/leo/software/data/projects` as read-only inputs.
- It requires an explicit `--software-owner` because legacy Software records have no owner.
- It creates a full backup before changing the Caddy data worktree.
- It preserves the existing Caddy repository's branch, remote, commits, and project paths.
- It converts current Caddy JSON into the new versioned project schema and nests Caddy-specific fields under `caddy`.
- It reads Software YAML with the old normalization rules: filename-derived names, trimmed scalars, allowed type, numeric order, sanitized and deduplicated services, and all existing links and ports.
- It merges exact `(owner, name)` matches.
- Software-only records receive `caddy: null`.
- Caddy-only records receive deterministic default registry metadata and appear after explicitly ordered Software records.
- The migration converts `shared` to private ownership by setting no sharing state and reports each conversion.
- The migration rejects templates until they are converted to an owned project or removed. Templates have no valid meaning in the new access model.
- Invalid Software names require an explicit mapping file. Migration does not silently rename projects.
- It validates Zitadel mappings, Linux accounts, project names, services, domains, and global ports before writing.
- It never imports `data/users.yml`, plaintext passwords, or old browser sessions.
- Dry-run is the default. `--apply` performs one schema-migration commit, writes `migrations/legacy-v1.json`, and refuses a second run.
- The old Caddy daemon and Software service stop only after the new daemon validates the migrated store and loads an equivalent Caddy configuration.

## Approach

### Process layout

```text
Browser
  -> Caddy HTTPS
  -> project-registryd loopback HTTP
  -> Zitadel

project-registry CLI
  -> /run/project-registry/<actor>.sock
  -> project-registryd

project-registryd
  -> Git-backed project store
  -> caddy validate
  -> Caddy admin API /load
  -> runuser <owner> systemctl --user
```

### Dependency direction

- `project` owns project data and mutation rules. It depends on interfaces for persistence and desired-state publication.
- `project-store` implements project persistence with `git-store`.
- `access` owns role comparisons and authorization. It depends only on actor, owner, and role values.
- `identity` defines user-directory needs. `zitadel` implements them.
- `caddy` reads validated project values and publishes generated configuration. It does not mutate project records.
- `service` owns allowlist and action rules. `user-systemd` implements process execution.
- `api` and `cli` translate requests into context use cases. They do not implement access, project, Caddy, or service rules.
- `runtime` composes concrete adapters, starts workers/listeners, and owns lifecycle state.
- `ui` consumes the API contract and contains no server authority.

### Project mutation flow

1. Establish the actor from the Unix socket or OIDC session.
2. Resolve current Zitadel roles for the actor and selected owner.
3. Authorize the operation.
4. Load and validate the complete current registry.
5. Apply the requested change and check project, service, domain, and port invariants.
6. Check the caller's expected Git revision.
7. Commit the project change through the serialized Git queue.
8. If generated Caddy output changed, queue generation, validation, and reload for the committed revision.
9. Return separate registry commit, Git push, and Caddy application states.

### Caddy application flow

1. Read the complete validated project registry at one Git revision.
2. Project active Caddy settings into deterministic routes.
3. Add docs, browse, static, proxy, access, and OIDC handlers.
4. Generate full Caddy JSON.
5. Validate it with the configured Caddy binary.
6. POST the validated JSON to the configured admin `/load` endpoint.
7. Mark that revision applied only after a successful response.
8. Keep the prior live config and retry if validation or reload fails.

### Failure handling

- Invalid current project files block readiness and identify the affected safe relative paths.
- Git write or commit failure prevents Caddy application.
- Git push failure leaves the local authoritative commit intact and reports push degradation separately.
- Zitadel lookup failure denies new privileged actions and does not expose cached hidden projects.
- A missing Linux account prevents socket creation and systemd actions for that owner.
- Caddy validation or reload failure leaves the desired revision pending while the last valid live configuration stays active.
- A systemd failure affects only that action and returns a fresh status or explicit query failure.
- Workers use bounded retries and serialized queues so concurrent users cannot mix Git commits or Caddy loads.

### Release sequence

1. Implement and test each bounded context in Project Registry while both old services continue running.
2. Provision the Project Registry Zitadel application and roles.
3. Build migration fixtures from the Software YAML and a copy of the Caddy data repository.
4. Run migration dry-runs and resolve templates, invalid names, users, domains, and ports.
5. Stop `caddy-projectsd` briefly, back up its data repository, and apply the schema migration.
6. Start `project-registryd` with the migrated repository and validation enabled but Caddy reload disabled.
7. Compare generated Caddy JSON with the current accepted configuration.
8. Enable reload, verify all routes, logins, docs, and services, then switch the public UI route.
9. Stop the old Software service.
10. Remove the old Caddy sockets and service only after CLI and UI parity checks pass.
11. Keep backups and old source/data repositories read-only through the rollback period.
